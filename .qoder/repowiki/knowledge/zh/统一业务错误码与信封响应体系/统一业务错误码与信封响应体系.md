本仓库在后端 FastAPI 与前端 axios 之间建立了一套端到端的统一错误处理机制，核心围绕「业务错误码 + 统一信封」展开。

## 后端：BusinessError + ErrorCode 集中定义
- backend/app/core/errors.py 定义 ErrorCode 常量类（按模块分组：通用/认证、课件、分类、标签、素材、访问令牌、AI 搜索），并通过 _HTTP_BY_CODE 字典将每个业务码映射到 HTTP 状态码；BusinessError 继承 fastapi.HTTPException，把 {code, message, data} 塞进 detail。
- backend/app/main.py 注册两个全局异常处理器：
  - @app.exception_handler(BusinessError) → 调用 schemas.envelope_or_business 包装成 {code, message, data, requestId} 信封返回。
  - @app.exception_handler(RateLimitExceeded) → 直接调用 fail("rate_limited", ...) 构造信封并返回 429。
- backend/app/schemas/__init__.py 提供 ok() / fail() / envelope_or_business() 三个构造器以及 Envelope Pydantic 模型，确保所有成功/失败响应都走同一 JSON 结构。
- 限流通过 slowapi 实现，backend/app/core/rate_limit.py 暴露 rate_limit(spec, key="ip|session") 装饰器，支持基于 IP 或 JWT sub 的键函数。

## 业务层使用模式
各 API 路由在参数校验失败、资源不存在、权限不足等场景下直接 raise BusinessError(ErrorCode.XXX, msg)，例如：
- public/coursewares.py：ACL 锁定、令牌无效时抛出 COURSEWARE_ACL_LOCKED / INVALID_TOKEN。
- public/materials.py：素材缺失、预览不可用时抛出 MATERIAL_STORAGE_UNAVAILABLE / MATERIAL_NOT_FOUND。
- admin/auth.py：管理令牌无效抛 INVALID_ADMIN_TOKEN。
- admin/materials.py：存储不可用抛 MATERIAL_STORAGE_UNAVAILABLE。

## 前端：axios 拦截器统一解包
- frontend/src/api/client.ts 创建 axios 实例，请求拦截器自动注入 X-Request-Id；响应拦截器检查 envelope 的 code：
  - code !== "ok" → 构造带 code / status 属性的 Error 并抛出，供上层 React Query / Toast 统一捕获。
  - 网络异常 → 从 err.response.data.code 回退为 http_${status}，message 取 body.message || err.message || "网络异常"。
- 调用方只需 .then(r => r.data) 即可拿到业务数据，无需重复判断。

## 架构约定
1. 禁止裸 raise Exception：业务异常一律通过 BusinessError(ErrorCode.XXX, message) 表达，由全局处理器统一封装。
2. 错误码即契约：新增错误码必须在 ErrorCode 中声明并在 _HTTP_BY_CODE 中映射对应 HTTP 状态码，保持与 API 规范一致。
3. requestId 贯穿链路：后端中间件生成/透传 X-Request-Id，前端拦截器也主动注入，便于日志追踪。
4. 限流异常单独处理：SlowAPI 的 RateLimitExceeded 不走 BusinessError 路径，由专用 handler 返回 rate_limited 信封。
5. 前端只认 envelope.code：不依赖 HTTP 状态码做业务分支，统一以 code === "ok" 作为成功判定。
